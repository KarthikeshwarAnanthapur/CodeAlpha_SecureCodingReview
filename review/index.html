Manual Code Inspection Method

This project uses manual code inspection to identify vulnerabilities — carefully reading through source code line by line to spot insecure patterns, unsafe function calls, missing validations, and exposed secrets without running automated tools.

Example 1 — Hardcoded Credentials
Language: JavaScript (Node.js)
Critical

⚠ Vulnerable Code

vulnerable // config.js const config = { db_host: 'localhost', db_user: 'root', db_pass: 'admin123', // ❌ api_key: 'sk-abc9876xyz' // ❌ }; module.exports = config;

✓ Secure Code

secure // config.js require('dotenv').config(); const config = { db_host: process.env.DB_HOST, db_user: process.env.DB_USER, db_pass: process.env.DB_PASS, // ✅ api_key: process.env.API_KEY // ✅ }; module.exports = config;

🔍 Issue Identified

Credentials are hardcoded directly in source code. If this file is committed to a public repository (e.g., GitHub), attackers immediately have access to the database and API services. This was identified during manual code review of the config.js file.

🛠 Remediation Steps

  • Move all credentials to a .env file and use the dotenv library to load them
  • Add .env to .gitignore so it is never committed
  • Rotate any credentials that were previously exposed immediately
  • Use a secrets manager (AWS Secrets Manager, Azure Key Vault) for production
  • Run git-secrets or similar tools to prevent future leaks
Example 2 — Unsafe innerHTML (XSS)
Language: JavaScript (Frontend)
High

⚠ Vulnerable Code

vulnerable // search.js function displayResult(userInput) { const div = document .getElementById('results'); // ❌ Executes embedded scripts! div.innerHTML = `You searched: ${userInput}`; }

✓ Secure Code

secure // search.js function displayResult(userInput) { const div = document .getElementById('results'); // ✅ Treats input as plain text div.textContent = `You searched: ${userInput}`; }

🔍 Issue Identified

Using innerHTML with untrusted user input allows attackers to inject HTML and JavaScript. For example, submitting <img src=x onerror="alert(document.cookie)"> would execute malicious code and steal session cookies.

🛠 Remediation Steps

  • Replace innerHTML with textContent whenever inserting plain text
  • If HTML rendering is truly needed, use a sanitization library like DOMPurify
  • Implement a Content Security Policy (CSP) header to restrict script execution
  • Encode all user-supplied data before rendering it in the browser
  • Validate and allowlist expected input formats on the server side
Example 3 — Weak Input Validation
Language: JavaScript (Node.js / Express)
Medium

⚠ Vulnerable Code

vulnerable // register.js (Express route) app.post('/register', (req, res) => { const { email, age, pass } = req.body; // ❌ No validation at all db.createUser({ email, age, pass }); res.send('User created'); });

✓ Secure Code

secure // register.js (Express route) const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/; app.post('/register', (req, res) => { const { email, age, pass } = req.body; if (!emailRegex.test(email)) return res.status(400).send('Bad email'); if (!Number.isInteger(age) || age < 0) return res.status(400).send('Bad age'); if (pass.length < 12) return res.status(400).send('Weak pass'); db.createUser({ email, age, pass }); // ✅ res.send('User created'); });

🔍 Issue Identified

The registration endpoint accepts and stores user data with absolutely no validation. This allows attackers to submit invalid emails, negative ages, empty passwords, or arbitrarily long strings that could crash the database or be used for injection attacks.

🛠 Remediation Steps

  • Always validate all user input on the server side — never trust client-side validation alone
  • Use schema validation libraries like Joi, Zod, or express-validator
  • Enforce minimum password length (12+ characters) with complexity requirements
  • Reject unexpected data types and out-of-range values with clear error messages
  • Return generic error messages to users; log detailed errors server-side only
